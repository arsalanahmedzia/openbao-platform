# ADR 0002: In-cluster S3 with SeaweedFS for PostgreSQL backups

- Status: accepted
- Date: 2026-10-25
- Evidence: [`02-storage-pods.txt`](../evidence/02-storage-pods.txt), [`02-bucket-job.txt`](../evidence/02-bucket-job.txt), [`02-s3-roundtrip.txt`](../evidence/02-s3-roundtrip.txt)

## Problem

CloudNativePG, through the Barman Cloud plugin, writes base backups and WAL
(the PostgreSQL transaction log) to S3-compatible object storage. Point-in-time
recovery replays WAL from that storage, so the platform needs an S3 endpoint.
The demo runs in a GitHub Codespace with a kind cluster: no cloud account, no
cost, and everything must be installed by Flux from Git.

## Options

1. **Cloud S3 (AWS S3 or similar)**: durable, off-cluster (backups survive the
   cluster), but needs a cloud account, costs money, and needs credentials
   from outside the repo.
2. **MinIO**: well-known S3-compatible server. The upstream project has moved
   its community edition to source-only / maintenance mode, so a pinned,
   maintained container image is no longer a given.
3. **SeaweedFS**: S3-compatible, Apache-2.0, actively released, a single
   container (`weed server -s3`) runs all components, small footprint.

## Choice

SeaweedFS 4.48, one pod in namespace `storage` (layer `infra-storage`), S3 API
on `http://seaweedfs.storage.svc.cluster.local:8333`. One identity (`backup`)
from a SOPS-encrypted identities file; the same key pair is given to
PostgreSQL as Secret `databases/s3-credentials`. A Job creates the bucket
`pg-backups` (idempotent). Credentials are generated by `scripts/setup/s3-secrets.sh`.

## Trade-off

- **Single replica**: if the SeaweedFS pod or its node is down, backups and WAL
  archiving pause until it is back (PostgreSQL keeps WAL locally meanwhile).
- **Data lost with the cluster**: data sits on one node's local-path volume.
  Deleting the cluster or losing that node deletes all backups. Backups that
  live in the same cluster as the database do not protect against losing the
  cluster; production would use off-cluster object storage (option 1).
- **No TLS inside the cluster**: S3 traffic is plain HTTP. It never leaves the
  cluster (Service type ClusterIP), but any pod in the cluster could read it on
  the network. Production would enable TLS (a cert-manager certificate) and
  NetworkPolicies limiting who can reach port 8333.
- **Static credentials**: one long-lived key pair; rotation means re-running
  `scripts/setup/s3-secrets.sh --force` and restarting SeaweedFS.
