# ADR 0003: HA PostgreSQL with CloudNativePG, backups through the Barman Cloud plugin

- Status: accepted
- Date: 2026-10-25

## Problem

OpenBao stores all its data in PostgreSQL. The database must keep working when
one node fails, and it must be restorable to a point in time (for example just
before a bad change). Everything is managed by Flux; the demo runs on a kind
cluster with 3 worker nodes in a 16 GB Codespace.

## Options

**Running PostgreSQL**
1. Single PostgreSQL pod (StatefulSet): simple, but a node failure stops the database.
2. Helm chart with replication (e.g. Bitnami): replication, but failover and
   backups are left to extra tools.
3. **CloudNativePG operator**: one `Cluster` object; the operator handles
   replication, automatic failover, Services for primary/replicas, TLS between
   instances, generated credentials, backups and recovery.

**Backups**
1. Volume snapshots: need a CSI driver with snapshot support (kind's
   local-path has none), and snapshots stay in the cluster.
2. In-tree `barmanObjectStore` in the Cluster: deprecated in favour of plugins.
3. **Barman Cloud plugin** (`ObjectStore` + `method: plugin`): base backups and
   continuous WAL archiving to S3; the supported way for current CloudNativePG.

## Choice

- CloudNativePG 1.30.1, Cluster `databases/pg-openbao`, PostgreSQL 18.6 (image
  pinned to the operator's default, ADR 0001).
- **3 instances** (1 primary, 2 replicas): one node can fail and there is still
  a primary plus a replica; with 2 instances a failover would leave no replica.
- **Anti-affinity `required` on `kubernetes.io/hostname`**: never two instances
  on the same node, otherwise one node failure could take out two copies. With
  3 workers each worker runs exactly one instance. `preferred` (the default)
  would allow sharing a node when the scheduler finds it convenient.
- **Asynchronous replication** (default): a write is confirmed by the primary
  alone.
- **Backups**: plugin-barman-cloud v0.15.1, ObjectStore `pg-backups`
  (`s3://pg-backups/`, gzip, retention 7 days), continuous WAL archiving
  (`isWALArchiver: true`, `archive_timeout: 5min`), a daily ScheduledBackup at
  02:00 UTC and one immediate Backup at creation.
- **Credentials**: generated by the operator (`pg-openbao-app`); no password in Git.
  (Changed by ADR 0004: the password of `openbao` now comes from the SOPS
  Secret `pg-openbao-openbao` through `bootstrap.initdb.secret`.)
- Restores go into a new cluster from `docs/runbooks/restore-example.yaml`,
  applied by hand (not in a Flux path), without WAL archiving.

Measured on 2026-10-25 (evidence `docs/evidence/03-*.txt`): primary pod
deleted -> replica promoted after 7 s, cluster 3/3 healthy after 18 s;
point-in-time restore of a small database in about 70 s, exact to the target
time (row before the target present, row after it absent).

## Trade-offs

- **Single S3 pod in the same cluster** (ADR 0002): while SeaweedFS is down, WAL
  waits on the primary's disk and no base backup can run; losing the cluster
  or SeaweedFS's node loses all backups. Production: off-cluster object storage,
  ideally in another region.
- **RPO (data loss on a total loss of the cluster)**: up to the WAL not yet
  archived. On a busy database WAL files fill and ship quickly; on an idle one
  `archive_timeout` forces a switch every 5 minutes, so up to about 5 minutes.
  A lower `archive_timeout` lowers RPO but writes more (mostly empty) WAL files.
- **RPO on failover**: replication is asynchronous, so a transaction confirmed
  in the last moment before the primary dies may not have reached a replica.
  Synchronous replication (`minSyncReplicas: 1`) would avoid that at the cost of
  write latency and of blocking writes if no replica is reachable.
- **`required` anti-affinity**: while a worker is down its instance stays
  `Pending` (no spare node); the cluster runs with 2 instances meanwhile.
- **RTO of a restore** grows with database size and with the amount of WAL
  since the last base backup (daily backups: up to a day of WAL to replay).
- **Demo sizing**: 256Mi request / 512Mi limit, `shared_buffers` 128MB, 5Gi
  local-path volumes (size not enforced, data tied to one node each). Observed
  128-373 MiB per PostgreSQL container (including file cache), no restarts.
  Production needs more memory, real disks with snapshots, and monitoring of
  archiving and replication lag.
